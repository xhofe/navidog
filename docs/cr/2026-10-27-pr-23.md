## 结论先说

**方向对，但这一版不该按现在的状态合并。**

对的部分要保留：

- 一个数据库一个 crate、`Cargo.toml` 分开、feature crate 只把三个驱动当 **dev-dependency**，`scripts/check-deps.sh` 同步扩到 9 个 crate——依赖方向是干净的（`check-deps.sh` 通过）。
- 目录 SQL 真的搬走了：`crates/navidog-db/src/metadata.rs` 从 614 行降到 172 行，只剩结果集读取，MySQL/PostgreSQL/SQLite 的 `information_schema` / `pg_catalog` / `sqlite_schema` 查询各归其位。这是本次最有价值的改动。
- `ContextSelection`、`prepare_database_sql`、`session_context_sql` 这类“用能力代替产品名”的抽象，比原来的 `match dialect` 好。
- 关键字表搬家没有丢词：旧表 266 条 = `COMMON` 86 + mysql 75 + postgres 62 + sqlite 43，逐条比对无缺失。
- `cargo fmt --all --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`scripts/check-i18n.sh`、`scripts/check-raw-px.sh`、`scripts/check-deps.sh` 全部通过；`navidog-sql` / `navidog-mysql` / `navidog-postgres` / `navidog-sqlite` / `navidog-db` / `navidog-schema` / `navidog-util` 的 lib 测试通过。

问题集中在三点，下面按严重度展开：

1. **PR 的核心承诺没做到，而且比改之前更弱**：枚举换成了 `&'static str`，49 处界面/规划代码按产品名比较字符串，反而丢掉了编译期穷尽检查。文档（`CONTEXT.md`、`docs/progress.md`、`docs/design/db/README.md`）却写着“不按产品名分支”。
2. **`Relational` 的目录方法从“能用的默认实现”变成了“返回错误字符串的桩”**：漏实现由编译错误退化成运行时错误，同时换来 3 份逐字重复的 51 行转发样板。
3. **同一件事有三套机制**：`Dialect` 能力方法、`DriverInfo` 布尔标志、`dialect.id()` 字符串比较。`Lex` 里的词法标志已经存在，`grid/src/filter.rs` 却重新用 `id() == "mysql"` 推反斜杠转义。

## A. 架构

### A-01 `Dialect::id()` 是这次改动最该删的东西

```21:21:crates/navidog-sql/src/dialect.rs
    fn id(&self) -> &'static str;
```

它唯一的消费方式就是按产品名比较字符串——生产代码 49 处（designer 29、query 8、grid 6、schema 5、db 1），另有 4 处 `match d.id() { "mysql" => …, "postgres" => …, _ => … }`。`grep -rn 'id()'` 全仓，除测试断言里当消息用，没有任何“持久化 / 日志 / 展示”的消费者。也就是说：`id()` 存在的全部意义就是让界面知道“你是哪个产品”，而 PR 描述写的是

> Replace the `Dialect` enum with a trait. The scanner reads lexical flags and does not name a product.

改动前后对比要说清楚，别把这次改动说成“消灭了产品名分支”——它没有，改动前也一样按产品分支。真正的差别是**类型安全**：改动前写 `dialect == Dialect::Postgres` 或 `match dialect { … }`，走的是同一个类型，`Dialect::Postgress` 这种拼写错误编译期就报，`match` 分支缺一个变体也会报。改动后：

- 没有穷尽检查，新增 Oracle 后所有 `id() == "…"` 静默走 else 分支；
- 拼错 `"postgres "` 编译通过、运行错分；
- 能力抽象（`like_text_cast()` 等）有了，但 `id()` 让“再加一个 `if` 就完事”变得比“加一个 trait 方法”更容易，抽象会持续被绕过。

证据（同一个文件、同一个结构体字面量里两种写法并存）：

```142:146:crates/navidog-query/src/format.rs
            postgres: dialect.as_ref().is_some_and(|d| d.has_schemas()),
            mysql: dialect.as_ref().is_some_and(|d| d.id() == "mysql"),
```

```128:135:crates/navidog-query/src/run.rs
            database: (dialect.id() == "postgres")
                .then(|| info.database.clone())
                .flatten(),
            schema: None,
```
同一个 `SessionContext::read` 里，往下三行又改用 `dialect.context_selection() == ContextSelection::Schema`。

而 `SessionContext::read` 的错误文案更直接地暴露了问题：

```144:144:crates/navidog-query/src/run.rs
            return Err(DbError::msg("SQLite has no USE/search_path context"));
```
条件是“这个方言没有会话上下文 SQL”，文案却写死 SQLite；将来接入没有 `USE` 的库，用户会被告知“SQLite 不支持”。

**改法**：删掉 `id()`（或改成 `#[doc(hidden)] fn kind(&self) -> DbKind` 并只允许在一个 `match` 里出现、返回编译期穷尽的配套枚举）。把 49 处逐条换成能力方法，例如：

| 现状 | 应改为 |
| --- | --- |
| `dialect.id() == "mysql"`（`commit.rs:83`，MySQL 的 UPDATE 只报 changed rows） | `fn counts_changed_rows(&self) -> bool` |
| `dialect.id() == "postgres"`（`run.rs:132`，会话已固定在某个库） | 已有的 `context_selection() == Schema` |
| `dialect.id() != "mysql"`（`structured.rs:689`，索引用独立 `CREATE INDEX`） | 已有的 `standalone_indexes()` |
| `dialect.id() == "sqlite"`（`grid/menu.rs:89`、`panel.rs:721`） | 已有的 `exposes_rowid()` / `rebuilds_tables()` |
| `d.id() == "mysql"`（`schema/options.rs:240,308`、`designer/panel/options.rs:8`） | `fn table_option_keys(&self) -> &'static [&'static str]` + 选项解析下移到方言 crate |
| `dialect.id() == "postgres"`（`filter.rs:302,515`，`::text` 强制转换） | 已有的 `like_text_cast()` |

工作量集中在 designer/panel/view.rs（12 处）与 schema/properties.rs（4 处），大多是“魔术下标 + 产品名”组合，见 S-01。

### A-02 文档承诺与实现不符（必须改掉其中一边）

同一 PR 里写了：

- `CONTEXT.md`：方言“……界面只问这些方法或 `DriverInfo` 上的标志，**不按产品名分支**。”
- `docs/progress.md`：“……新数据库加 crate 并在 session 注册，**不必改各界面里的产品名分支**。”
- `docs/design/db/README.md`：“**不要在 grid、query、designer 里按产品名分支**；界面读方言能力方法或 `DriverInfo` 上的标志。”

对照 A-01 的 49 处，这三处文档都是错的。这不是措辞问题：`db/README.md` 是后来者接 M14（Oracle / SQL Server）时唯一的接入指南，照它做会立刻撞上一个 49 处的隐式契约。

**改法**：要么按 A-01 清干净再保留这几句，要么把它们改成“目前仍有 N 处按产品名分支，接入新库时需要一起改”，附录列出文件。二者选一，不要既写规则又不执行。

`docs/progress.md:34` 还多写了四个字：“**行为不变**”。实际有三处用户可见的行为变化（PR 描述里自动生成的 “Behavior Changes” 段落也承认了）：

1. 没有方言时补全为空：`query/completion.rs:269` 从 `e.dialect(cx).unwrap_or(Dialect::MySql)` 改成 `let Some(dialect) = … else { 返回空 }`。孤立查询编辑器（连接已删除）以前至少能补 MySQL 关键字，现在什么都不给。
2. 未绑定网格不再引用字符串：`grid/edit.rs:40:46` 走 `unbound_text()`，raw 模式编辑器里是裸值而不是 `'值'`。
3. 表设计器标签页在连接消失后变成 `MissingConnection` 面板；`crates/navidog/tests/tabs.rs:30-39` 为此在测试里塞了一个假 sqlite 连接，否则拿不到真正的设计器面板。

三条都是合理的改进，但 `progress.md` 应该如实登记，而不是写“行为不变”。

### A-03 目录方法从“可用默认实现”退化成“运行时错误桩”

```304:307:crates/navidog-db/src/driver.rs
    // Catalog queries. The SQL lives in each database crate; these defaults only keep test
    // doubles compiling. A real session overrides them.
    fn list_databases(&mut self) -> BoxFuture<'_, DbResult<Vec<String>>> {
        Box::pin(async { Err(DbError::msg("This session does not list catalogs.")) })
    }
    …
    fn list_objects<'a>(…) -> BoxFuture<'a, DbResult<Vec<ObjectInfo>>> {
        Box::pin(async { Err(DbError::msg("This session does not list objects.")) })
    }
```

改动前这些默认实现是 `crate::metadata::list_databases(self)`——按 `dialect` 生成 SQL 并执行，**新驱动只要实现 `dialect()` 就自动有目录浏览**。改动后：

- 漏实现不再编译失败，而是用户点开表时看到一个英文报错；
- 7 个方法 × 3 个 crate 的转发样板（见 D-02）是这项改动的账单；
- 桩文案硬编码英文，但 `navidog-db` 明明有 `t!` 和 locale（同 crate 里 `database.operation_connection_retired` 就是走 `t!` 的）。12 处 `DbError::msg` vs 6 处 `t!`，本地化不一致。

**改法**（两条都行，但别停在现在这样）：

1. 拆出一个必实现的 `trait Catalog`（`list_databases`/`list_schemas`/`list_objects`/`object_ddl`/`table_columns`/`table_children`/`foreign_keys`/`outline`），`Relational: Catalog` 或 `fn catalog(&mut self) -> Option<&mut dyn Catalog>`；漏实现回到编译期。
2. 或者保留默认实现但改为 `Err(DbError::coded("navidog.catalog_unsupported", …))` 并走 i18n，同时在 `debug_assert!` 里拦住“真实驱动忘了实现”。桩文案至少不能是裸英文。

### A-04 god trait：`Dialect` 61 个方法、25 个布尔；`Relational` 13 个方法（8 个目录）

`crates/navidog-sql/src/dialect.rs` 现在有 61 个 trait 方法，其中 25 个返回 `bool`（19 个默认 `false`）、9 个返回 `Option`。`Relational` 则有 `list_databases`、`list_schemas`、`list_objects`、`object_ddl`、`table_columns`、`table_children`、`foreign_keys`、`outline`、`execute`、`execute_read`、`execute_statement`、`dialect`、`object_kinds`。

后果是可测的：新增一个数据库要实现 61 个方法里的 20 多个，其中 19 个 `false` 默认值只能靠“看 `impl Dialect for MysqlDialect` 抄一个”，不知道哪些默认值是对的。`DriverInfo` 又额外挂了 8 个布尔（`file_based`、`multi_host`、`supports_network`、`supports_ssl`、`chooses_ssl_mode`、`protocol_timeouts`、`connection_params`、`supports_ssh`、`per_database_sessions`），其中 `file_based` 与 `context_selection() == File` 是同一事实的两种表示、`per_database_sessions` 与 `context_selection() == Schema` 也是。

**改法**：把布尔收进一个 `#[derive(Default)] struct DialectFeatures { … }`（或按簇拆成 `Syntax` / `Lex` / `Session` / `Designer` 四个小组，各自一个 `fn features()`），新增数据库时编译器要求你给出完整结构体，读代码的人也能一眼看完“这个库支持什么”。布尔方法本身没罪，61 个平铺的方法是。

### A-07 静默兜底：新增库时无声失效


问题不在“手写”本身，而在**同一个 crate 里就有能正确做这件事的扫描器**（`crate::span::spans`，PR 自己还在 span.rs 顶部强调“每个 SQL 消费者都读这份 span，同一段 SQL 不会被读成两种样子”）。这段代码有明确的可复现失败：

- `CREATE TABLE IF NOT EXISTS app.actor (…)`（未加引号的库前缀）→ `tail` 以 `app` 开头，`forms` 里没有，返回 `None`，复制表直接失败；
- `CREATE TABLE "app"."actor" (…)`（带引号的库前缀）→ `tail` 以 `"app"` 开头，同上；
- `upper.find("CREATE TABLE")` 会命中注释或字符串里的 `CREATE TABLE`（SQLite 导出的 DDL 里带注释很常见）；
- 名字比 `old` 长且是它的前缀时（`actor` vs `actor_id`）没有边界检查，只靠 `starts_with` 加后缀拼接。

**改法**：用 `span::spans(ddl, self.lex())` 找到 `CREATE` 之后的 `TABLE`，跳过 `IF NOT EXISTS`，取下一个 `Word`/`QuotedIdent`（连同可能的 `QualifiedIdent`），按 span 范围替换。约 30 行，能正确覆盖引号/库前缀/注释，并且和其他 SQL 消费方用同一套词法。顺带给 `duplicate_table` 的 SQLite 分支补一个 `"app"."actor"` 形式的测试。

```rust
enum Assign { Set, Key }   // 或 fn assignments(dialect, values, is_key: bool)
```

同款：`drop_constraint_clause(&self, kind: &str, name)`：

```125:129:crates/navidog-sql/src/dialect.rs
    fn drop_constraint_clause(&self, _kind: &str, name: &str) -> Option<String> {
        Some(format!("DROP CONSTRAINT {}", self.quote_ident(name)))
    }
```
`"PRIMARY"` / `"FOREIGN"` / `"INDEX"` 是字符串（`crates/navidog-mysql/src/dialect.rs:93`），拼错就是 `_ => None` 静默返回“不知道”，设计器随后可能生成不完整迁移。这里应有枚举（`ConstraintKind`），编译器会逼你把三种都处理掉。

### S-04 `DriverInfo` 丢 `Debug`；宏里的 `futures::future::BoxFuture`

```81:81:crates/navidog-db/src/driver.rs
#[derive(Clone)]
pub struct DriverInfo {
```
改动前是 `#[derive(Clone, Debug)]`。因为 `Arc<dyn Dialect>` 不是 `Debug`，直接降级删了 `Debug`——这会让所有 `#[derive(Debug)]` 的持有者（以及 `dbg!`/`assert_eq!` 的报错信息）一起失效。正确做法是给 `Dialect: Debug` 加上 supertrait（三个实现都是无字段 unit struct，一行 `#[derive(Debug)]` + 一行 trait 声明），或者在 `DriverInfo` 上 `impl Debug` 手写跳过 `dialect`。

宏：

```209:211:crates/navidog-db/src/driver.rs
        fn ping(&mut $self) -> futures::future::BoxFuture<'_, $crate::DbResult<()>> {
```
同一个宏里，`DbResult` 走了 `$crate::`，`BoxFuture` 却直接写 `futures::future::`。这要求**展开方**必须有 `futures` 直接依赖（现在三个 crate 恰好有，但这是隐式契约，插件驱动或第三方驱动会编译失败）。改成 `$crate::BoxFuture`（在 `navidog-db` 里 `pub use futures::future::BoxFuture;`）或 `$crate::futures::BoxFuture`。

### S-05 小写法

- `fn dialect(&self) -> std::sync::Arc<dyn navidog_sql::Dialect> { std::sync::Arc::new(MysqlDialect) }`（`mysql/driver.rs:277`、`postgres/driver.rs:484`、`sqlite/driver.rs:201`）：文件顶部已经 `use std::sync::Arc;`，这里却又全限定写一遍；更重要是**每次调用新建一个 `Arc`**，而 `.dialect()` 有 44 个调用点（含每格渲染路径上的 `filter`/`delegate`）。方言是无状态 unit struct，用 `static MYSQL: MysqlDialect = MysqlDialect;` + 缓存 `Arc`（`OnceLock`）即可，或者把 trait 签名改成返回 `&'static dyn Dialect`。
- `&navidog_postgres::PostgresDialect.is_system_schema(s)`（`crates/navidog-db/tests/live.rs:170`）：对 unit struct 取 `&` 再自动解引用调用方法，可读性差，写成 `navidog_postgres::PostgresDialect.is_system_schema(s)`。
- `let raw = delegate.raw.then(|| delegate.dialect.clone()).flatten();`（`grid/menu.rs:107`）：`then(…).flatten()` 两层 `Option` 才能得到目标值；`if` 或 `then_some(...).flatten()` 更直接。全仓 `.then(|| …)` 共 44 处，本 PR 新增的几处（`grid/menu.rs:107`、`query/run.rs:133,157,161`）都是这种两层 `Option`。
- `owned_context_sql` / `toolbar_context_sql`（`query/run.rs:645-676`）的抽离很好，注释也解释了 `search_path` 的坑——这类注释应该在别的“按产品名分支”处也出现，而不是靠 `id()` 的简短比较。

### S-07 为宏把内部模块整块 `pub`


## 剩余已知问题

这一轮之后，本审查列的 30 条全部处理完毕。仍然存在、但不属于本次 PR 范围的：

- `Dialect` 48 个方法里仍有 8 个 `Option<String>` 形式的 SQL 产物（`rename_object`、`exclusive_lock_sql`、`table_owner_sql`、`session_context_sql`……）。它们本就是“给一段 SQL”，与 `features()` 的分工是清晰的。
- 关键字表是手抄的保留字集合，不是由官方文件生成的。来源写在文件头里；将来接 Oracle / SQL Server 时，建议每家补一份并用脚本生成。
- `navidog-schema` 的表选项**解析**（`mysql_span` / `pg_storage` / `pg_clause`）仍在通用 crate 里，只按 `TableOptionStyle` 分派。彻底的修法是把它连同选项键一起搬进各自的方言 crate，但那会形成 schema → 方言 crate 的依赖，轮不到本次 PR 决定。
- 表设计在 `enriches_from_catalog` / `rebuilds_tables` 下仍直接执行 PostgreSQL catalog SQL 和 SQLite 重建 SQL（`sqlite_schema`、`sqlite_sequence`、`PRAGMA`）。三个现有库的开关是对的；接入第四个数据库前把这些 SQL 移进方言方法。已记在 `docs/progress.md` 的临时偏差里。
